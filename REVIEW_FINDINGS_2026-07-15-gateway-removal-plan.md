## 1. Verdict

**Approve with corrections.** The core mechanism holds up against the fetched sources: podman-run docs and podman's `hosts.go` source show an explicit `--add-host ...:host-gateway` hard-fails creation when the address cannot be computed; the passt man page shows `--map-guest-addr` redirects to the host's global address (so a `0.0.0.0` bind is both necessary and sufficient); and the machinery slated for deletion is genuinely dead once the gateway goes. Three gaps must be fixed before implementation: hosts-file base inheritance (I1), a cutover that bricks non-box workspaces (I2), and an ungated Podman version floor (I3). The corrected plan in §5 addresses them without violating any non-negotiable product decision.

## 3. Answers to the review questions

**Q1 — Does Podman reliably support explicit `--add-host host.containers.internal:host-gateway` on the custom `isolate=true` rootless bridges used here?**
Supported per the fetched sources: `--add-host` is hosts-file-level (podman-run docs), and the substitution happens in `parseExtraHosts` regardless of network driver (`hosts.go:250-255`). IP selection priority, from `ip.go:50-98`: containers.conf `host_containers_internal_ip` override → gvproxy DNS on podman machine → pasta `PreferIP` (`169.254.1.2`) → host local IP for rootless. Reachability semantics verified from passt(1): `--map-guest-addr` redirects "to the address assigned to the guest with -a, or by default the host's **global address**" — wildcard-bound services reachable, loopback-only not. **Unverified platform assumptions:** that the box's nested podman actually uses pasta as the rootless-netns provider (containers.conf default `default_rootless_network_cmd="pasta"` per fetched docs; a box plan doc reports podman/stable ships pasta — delegated), and that `isolate=true` leaves the container→host path untouched (inferred from netavark's inter-bridge scope; not tested). The nested smoke is the right proof; corrected item 7 extends it.

**Q2 — Can the managed hosts machinery be deleted completely, or does Podman require a controlled `--hosts-file` base?**
Yes, but with a controlled base: `--hosts-file=none` (issue I1). The deleted machinery is `MINIMAL_HOSTS`, `writeMinimalHostsFile`, `minimalHostsFileIsExact`, `hasExactMinimalHostsPolicy` (`ploinky/cli/services/networkLifecycle.js:46-47, 347-418, 595-613` — observed). With an empty base, podman auto-adds localhost entries (`hosts.go:116-121` — verified, per podman issue #11411), so nothing else is needed. Without `--hosts-file=none`, the base defaults to the box's `/etc/hosts` and the duplicate-entry hazard of I1 applies.

**Q3 — Does explicit `host-gateway` fail container creation when it cannot be calculated, or could it be silently omitted?**
Fails hard — verified twice: podman-run docs ("there's no guarantee that Podman can determine the host-gateway address automatically, which will then cause Podman to **fail with an error message**") and the source error in `parseExtraHosts` (`hosts.go:250-255`: "unable to replace host-gateway ... host containers internal IP address is empty"). The **automatic** `host.containers.internal` entry is what gets silently skipped on failure (same docs), so the explicit spelling is the only one satisfying the plan's fail-hard decision. Note `host_containers_internal_ip="none"` in containers.conf also produces the hard error (empty IP → source error path) — fail-closed, acceptable.

**Q4 — Is `server.listen(port, "0.0.0.0")` the correct minimal bind, and does the outer publication contract still control physical-host/LAN exposure?**
Yes, with I7's nuance: the change narrows an existing wildcard bind rather than widening a loopback one (observed at `ploinky/cli/server/RoutingServer.js:735`). It matches all consumers: IPv4-only managed bridges, the pasta redirect (IPv4 `169.254.1.2`), host-mode `127.0.0.1`, and the TCP readiness probe. Physical exposure remains governed by the outer box publication plan, which this plan does not touch; the box run-args area was read (`ploinky/container/runtime-supervisor.mjs:1195-1240`) but the publication planner was not reviewed in depth — the plan keeps it unchanged, so nothing there needs to move.

**Q5 — Is the configured router port always available before managed agent creation, allowing removal of the silent `8080` fallback?**
For `ploinky start`: observed — `ensureRouterReadyForStart` persists `port: staticPort` via `mergeRoutingConfig` and gates on `waitForRouterReady` (`ploinky/cli/services/workspaceUtil.js:698-745`); that agent creation follows this gate is inferred from the call flow, not traced exhaustively. Monitor restarts run in workspaces where `routing.json` already exists (inferred). So replacing the `'8080'` fallback with a thrown error for managed modes is safe on normal paths and correctly loud on abnormal ones (ad-hoc agent creation in a workspace that never ran `start`).

**Q6 — Is keeping resource schema 2 while introducing status schema 3 internally coherent?**
Yes, if and only if the constants split (I8). Observed: the contract hash is an *agent* label; network labels carry no contract hash (`ploinky/cli/services/networkLifecycle.js:67-75`), so schema-2 bridges survive unchanged and are reused. Status schema 3 must be a new constant that only feeds `status()`.

**Q7 — Does changing only `runtimePolicy` correctly invalidate old agent containers without turning existing bridge resources into foreign collisions?**
Bridges: unaffected (Q6). Agents: they become **foreign, not drift** — observed at `ploinky/cli/services/networkLifecycle.js:1332-1336` and the throw at `ploinky/cli/services/docker/agentServiceManager.js:1549-1552` ("refusing to replace foreign/unsupported exact-name container"). Correct fail-closed behavior inside a box (boot cleanup removes old agents first); a hard refusal outside one — the release procedure must own that case (I2). Old agents are never silently adopted, consistent with the prior-review F2 remediation present in the worktree.

**Q8 — Does outer-box boot cleanup definitely remove the old gateway before its network attachments are reused?**
For boxes, yes — observed: `remove_managed_containers` force-removes all `io.assistos.ploinky.managed=1` containers at `container-image-builds/images/ploinky-box/entrypoint.sh:134` (definition at :82-97) before the box command executes, and gateway labels include `managed=1` (`ploinky/cli/services/networkLifecycle.js:77-86`). Networks are not containers and persist with valid labels. Note the cleanup matches the single `managed` label, not the full five-label set — broader than "exact-label", which is what is wanted here. It also fails closed on enumeration/removal errors, so a stuck old container prevents box start rather than being skipped.

**Q9 — Is releasing the `ploinky-router` DNS alias safe, considering its separate authentication meaning?**
As a transport name: the sweep subagent reported zero non-cli code building `http://ploinky-router` URLs **(delegated — not independently rerun)**. As identity, it must not move — observed in this session's greps: JWT issuer/audience across `ploinky/cli/server/security/tokens/RouterRequestTokenService.js:121`, `AgentAssertionService.js:88,108`, `UserDelegationGrantService.js:107-159`, `ploinky/cli/server/auth/localService.js:13`, `ploinky/Agent/lib/requestSignedTokens.mjs:43-63`, `ploinky/Agent/lib/agentAssertion.mjs:45`; the discovery target (`ploinky/cli/server/openAiAgentDiscovery.js:29` — read in context, a JWT-bound surface identity, not a hostname); MCP `clientInfo` (`ploinky/Agent/client/MCPBrowserClient.js:524`). Additionally soul-gateway assertions (`proxies/soul-gateway/src/runtime/backends/ploinky/agent-assertion.mjs:138-140`) and a Keycloak client id (`basic/keycloak/manifest.json:24`) **(delegated)**. Recommendation: keep the alias reservation (I6); if removed, nothing observed breaks.

**Q10 — Are there any production consumers of the current `gateway` status field?**
None found **(delegated)**: the sweep subagent reported zero `network status` JSON consumers outside `ploinky/cli` + tests, with the `schemaVersion` hits in `ploinky/container/runtime-supervisor.mjs:1030,1097` belonging to the supervisor's own publication-plan schema and soul-gateway `gateway:` hits being middleware scopes. Three of that agent's citations were spot-checked (all exact) but the consumer search itself was not rerun. Treat as high-confidence, delegated.

**Q11 — Which gateway-related helpers are truly dead after removal, and which still serve non-gateway Podman behavior?**
From the full read of `ploinky/cli/services/networkLifecycle.js` — **dead after removal:** image constants (:24-25), `gatewayContainerName` (:63-65), `expectedGatewayLabels` (:77-86), the `routerSocket` label (:21), `remoteShellCommand` (:108-115), the namespace-executor trio `resolveRemoteMachineName`/`ensureNamespaceExecutor`/`executeInRootlessNamespace` (:475-556; only callers are the gateway forwarding check :669 and probe :790-803), `assertRouterSocket` (:615-625), image pull/validate (:627-640), `assertGatewayForwardingDisabled` (:642-676), `assertGatewayRecord` (:678-765), `revalidateGatewayForMutation` (:767-778), the probe pair (:780-809), `podmanSelinuxEnabled` (:811-821, gateway-only callers), `ensureGateway` (:848-948), preflight's gateway checks and its `routerEnv` block (:969-999 — a grep for `.routerEnv` across `cli/` returned zero consumers; env injection happens via `buildRuntimeRouterEnv` at `agentServiceManager.js:1040`), the gateway branch of `rollbackResources` (:1004-1011), `reconcileManagedControlPlane` (:1052-1065; sole caller `agentServiceManager.js:1595`), the status gateway block (:1296-1322), the gateway arms of `pruneUnlocked` (:1369-1420), the minimal-hosts machinery (:46-47, 347-418, 595-613), and the `--no-hosts`/volume args (:1033-1039). ## 5. Corrected replacement plan

This section is a proposal. Changes from the reviewed plan are marked **[changed]** or **[added]**; unmarked text is approved as submitted.

1. Default/bridge agents receive `PLOINKY_ROUTER_HOST=host.containers.internal`, `PLOINKY_ROUTER_PORT=<configured RoutingServer port>`, and `PLOINKY_ROUTER_URL=http://host.containers.internal:<configured RoutingServer port>`. Host-mode agents continue using `127.0.0.1:<configured port>`. None-mode agents receive no router variables. **[added]** Managed-mode env resolution must throw when no configured router port is resolvable (from options or `routing.json`); delete the silent `'8080'` defaults in `buildRuntimeRouterEnv` and the bwrap/seatbelt env builders. All three variables are always injected together so host-var-blind consumers (`Agent/client/AgentMcpClient.mjs`) keep working via `PLOINKY_ROUTER_URL`.

2. Managed agent creation uses exactly `--add-host host.containers.internal:host-gateway` **[changed]** *plus* `--hosts-file=none`, so the hosts file is deterministic: the explicit mapping, Podman's automatic `localhost` entries, and the container's own name — nothing inherited from the box's `/etc/hosts` (Podman writes user and base entries without dedup, and the box file is expected to carry the outer runtime's conflicting `host.containers.internal` entry). Remove `--no-hosts` (documented as conflicting with `--add-host`), the managed `/etc/hosts` bind mount, the generated `managed-hosts` file, and all alternative address resolution. The reuse/contract policy check validates `HostConfig.ExtraHosts == ["host.containers.internal:host-gateway"]` and `--hosts-file=none` in `CreateCommand`, replacing `hasExactMinimalHostsPolicy`.

3. RoutingServer: bind explicitly to IPv4 `0.0.0.0:<port>` inside the box (**[added]** documenting that this narrows today's implicit wildcard bind and that the in-box router is intentionally IPv4-only). Remove `.ploinky/run/router.sock`, the Unix-to-loopback TCP relay, and its permission/cleanup lifecycle. Make startup readiness TCP-only (both `waitForRouterReady` call sites). Keep the existing outer-box publication policy unchanged.

4. Managed network lifecycle: remove the gateway image constants, container name, labels, socket identity, image pulls, validation, readiness probes, repair, reconciliation (including the `reconcileManagedControlPlane` call in the agent-reuse path), rollback, status, and prune logic; remove the namespace-executor and remote-machine code and `podmanSelinuxEnabled` (all gateway-only). Preserve rootless-Podman proof, bridge creation, `isolate=true`, locking, atomic agent replacement, network aliases, and multiple attachments. Remove the consumer-less `routerEnv` from network preflight. Change the contract hash `runtimePolicy` from `managed-hosts-v1` to `box-host-gateway-v1`.

5. Versioning/status: keep the resource label schema at 2 (bridge shape unchanged) **[changed]** as a constant *separate* from a new status schema 3 constant — do not bump the shared `NETWORK_SCHEMA_VERSION`, or every existing bridge becomes foreign. `network status --json` becomes `{ schemaVersion, workspaceHash, networks }` with no top-level `gateway` field (no consumers found; delegated sweep). Attachment ownership becomes `agent | unknown`. Prune only exact-owned empty networks.

6. Naming: **[changed]** keep the `RESERVED_NETWORK_ALIASES` entry for `ploinky-router` as one-line defense-in-depth (the string remains the JWT issuer/audience, discovery target, Keycloak client id, and MCP client name), with a comment that it is reserved as an identity, not a route. Do not alter `ploinky-router` anywhere it is an identity.

7. Gateway artifact: delete `container-image-builds/images/ploinky-network-gateway`, its publication workflow, its README sections, and its image-definition test block. Replace the box-image workflow's `slirp4netns:allow_host_loopback` smoke with a real nested-Podman `host-gateway` smoke, **[added]** which must also gate the inner Podman version at ≥ 5.4 (pasta `--map-guest-addr` default arrived in 5.3; `--hosts-file` in 5.4) and assert the agent's `/etc/hosts` contains exactly one `host.containers.internal` entry. **[added]** Record the explicit decision that the already-published Docker Hub image is left in place.

8. Security documentation: **[changed]** rewrite, in the same change, DS004 (lines 74 and 94-113, including deleting the uncommitted namespace-proof paragraph) and DS011:133-137 — both currently mandate the localhost-only hosts file and name `host.containers.internal` as an alias to be removed — plus `docs/code-derived-agent-lifecycle.md` and the stale contract-2 line in `container-image-builds/README.md`. State that bridge-to-bridge isolation remains; that agents can reach services bound to the box gateway address or wildcard interfaces (per passt(1), `--map-guest-addr` traffic lands on the host's global address, so loopback-only services are *not* expected to be reachable — still do not claim this in docs until the smoke proves it); that routed agent-to-agent MCP calls remain JWT- and policy-protected; and that direct calls to other reachable box services bypass router authorization and those services must protect themselves.

9. Cutover: require an outer Ploinky-box restart before new agents start; rely on the entrypoint's `managed=1` boot cleanup to remove old agents and the gateway. Do not add legacy cleanup or adoption branches to runtime code. **[added]** For non-box workspaces, the one-time release procedure must mandate `ploinky destroy` before upgrading (old-contract agents otherwise hard-fail with the intentional `refusing to replace foreign/unsupported exact-name container` error, which the release note documents alongside stale `router.sock`, `managed-hosts`, and cached gateway-image residue). **[added]** Record that prior-review findings F15/F16 are resolved by this deletion.

10. Tests: everything in the reviewed item 10, **[added]** plus the hosts-file exactness assertion in the smoke, the managed-mode missing-port hard-fail unit test, a schema-2 bridge continuity test across the contract change, the pinned refusal-error test for old-contract agents, the `ExtraHosts`/`--hosts-file` reuse-policy unit tests, and a removal gate extended to `127.0.0.1:8080` transport fallbacks and `allow_host_loopback`/`host.docker.internal` in `ploinky/cli`.

## Review conclusion

The plan is approved with the corrections above. The two decisive amendments are `--hosts-file=none` alongside the explicit `--add-host` (I1) and an owned cutover path for non-box workspaces (I2); the version-floor gate (I3) makes the platform dependency explicit instead of incidental. Everything else in the reviewed plan was validated against the working tree — including the ~1,650 lines of uncommitted remediation changes — and against Podman documentation and source. No files other than this findings document were created, and nothing was implemented.
