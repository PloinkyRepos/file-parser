# Ploinky Box Clean-Default Rebuild Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild Ploinky Box from the recorded clean default-branch tips, preserving the explicitly required clean-start product behavior while introducing the contract-5 outer runtime, isolated private routing, explicit product services, and native multi-architecture supply-chain gates. No predecessor Box state, schema, or encrypted payload is carried forward automatically; an allowed existing external resource is selected only explicitly under its authorized release gate.

**Architecture:** A fixed, source-free outer Box runs rootless Podman and mounts current Ploinky source read-only. RoutingServer is the only HTTP/WebSocket/MCP edge. Public/control traffic terminates on 8080; private bridge traffic reaches an unmounted Unix socket through a byte-only forwarder bound to the exact rootless transport address and an exact-tuple nftables allowlist. Immutable content-addressed generations and request-bound authorization-to-dial leases coordinate routes, policies, networks, firewall state, and product instances.

**Tech Stack:** Node.js 20+, Bash, rootless Podman 5.4+, Netavark, Aardvark DNS, pasta, nftables, OCI multi-architecture images, GitHub Actions, Node test runner, Python unittest, Playwright, Cloudflare Tunnel API/connector, LiveKit, OnlyOffice, Umami, and GPTResearcher.

## 2. Decision Records

### DR-Q8 — Isolated Forwarding/Firewall Architecture

**Decision:** Unconditionally select DS004 Question #8 option 2 for this rebuild: a new isolated forwarding/firewall architecture. The exact historical listener model is not feasible on the tested rootless Podman/Netavark topology, and it is not retained as a fallback. The real native arm64 engine spike below is sufficient to choose the architecture for planning. Before any production-behavior slice begins, Gate G0 must reproduce the same positive and negative model on native Linux amd64 and arm64 and an independent consequential security reviewer must accept the design and evidence; failure stops all work after the spike. Those are implementation-authorization gates for the selected design, not permission to fall back to a public/wildcard/gateway listener.

#### Native evidence already obtained

The architecture spike ran on macOS arm64 with a Linux arm64 rootless Podman machine using Podman `5.8.2`, Netavark `1.17.2`, Aardvark `1.17.0`, and pasta `20260120`. It used the immutable local contract-5 image ID `89b5a3b10679fae9fe5d8139a00ba1967393c2b7e8bf3f41bf9603d64c5a93db`; its entrypoint checksum exactly matched `container-image-builds/main` (`bfaadf5c85f2275f8f0d21ca12c3c0604a911ef2c986a6c63d04cd2e5103402a`). The outer inspect showed exactly `127.0.0.1:19080 -> 8080/tcp` and `0.0.0.0:7882 -> 7882/udp`; `19080` was only the spike-selected host port, not a fixed contract value. Two isolated managed bridges were the minimum positive fixture, and an adversarial foreign attachment established the allowed/denied reachability model. The production acceptance harness must dynamically enumerate every eligible schema-2 managed bridge and every exact active managed instance from engine inspection; it is not allowed to stop after two fixtures. All named spike containers and volumes were removed. A fresh build was blocked by an unrelated nearly-full Podman VM; no cache or unrelated image was pruned.

#### Listener and socket model

| Endpoint | Owner | Binding | Exposure rule |
|---|---|---|---|
| Public/control | `RoutingServer` | `0.0.0.0:8080` inside the outer Box | Published only as `127.0.0.1:<selected-host-port>` |
| Host capability | `RoutingServer` | `127.0.0.1:8081` in the outer/main network namespace | Host-mode current LiveKit instance only; still requires JWT/policy |
| Private request handler | `RoutingServer` | `/home/podman/.config/ploinky-private/router-private.sock` | Directory `0700`, socket `0600`, never mounted into nested containers |
| Detailed health | `RoutingServer` | `/home/podman/.config/ploinky-private/router-health.sock` | Directory `0700`, socket `0600`, never workspace-mounted |
| Bridge forwarder | Ploinky-core-supervised byte proxy | exact discovered transport IPv4:`8081` in `podman unshare --rootless-netns` | Not outer-published; reachable only through verified nftables tuples |

`/run/ploinky` cannot contain the private UDS because `podman unshare --rootless-netns` masks `/run`. The forwarder is a small `node:net` byte proxy. It does not parse HTTP, authenticate, authorize, resolve names, inspect bodies, or log payloads. It connects only to the private UDS. It validates its executable checksum, parent PID plus `/proc/<pid>/stat` start time, and exact listener ownership; it exits on parent mismatch. Router restart may recreate its sockets and launch a new supervised forwarder only after read-only verification of the immutable active generation and firewall. It never creates/deletes networks or silently repairs nftables drift.

#### Firewall contract

- Own one stable table, `inet ploinky_private`, with an input base chain at priority `-20`.
- Generate a canonical exact-tuple set by engine-enumerating every current-workspace/current-generation schema-2 managed bridge, all of its eligible active managed attachments, and each attachment's immutable instance ID, interface, and inspected IPv4. Each eligible attachment maps one-to-one to one allow tuple binding destination transport IPv4, TCP port `8081`, exact managed bridge interface, and exact inspected source IPv4. Reject missing, duplicate, or extra tuples before activation. A final owned rule drops all other traffic to transport IPv4:`8081`; unrelated traffic is unaffected.
- Never authorize a subnet, container name, DNS alias, claimed hostname, source IP alone, or manifest text. Source reachability is defense in depth; signed request identity remains authoritative.
- Render the whole owned table, run `nft --check -f`, apply in one `nft -f` transaction, read back with `nft -j`, normalize away kernel handles, and compare the semantic SHA-256. Execute nft through argv, never a shell string.
- Firewall rules, forwarder state, network state, route state, and enabled-instance identity are one content-addressed private-lane generation. The generation ID is the canonical content SHA-256 (`64` lowercase hex), not a UUID.
- Enumeration, parse, apply, readback, checksum, listener, PID, or forwarder drift closes the lane and leaves the route inactive. There is no automatic repair and no fallback to a predecessor generation.

#### Atomic lifecycle and lock order

The lock order is always edge-apply lock, then network-lifecycle lock. Code and tests must reject or structurally prevent the inverse order.

Replacement transaction for a bridged instance: stage inactive route/registry state; create the replacement stopped; inspect its immutable ID, exact config, IP, and bridge; render the old+new tuple set; preflight/apply/read back firewall; start that exact ID; pass health; verify the forwarder; commit private-lane and edge selectors last; activate the replacement route; render/apply/read back a set without the old tuple; only then delete the old container. If old-tuple removal fails, close the lane and retain the old container. Disable order is route/claims inactive, remove and verify tuple, then delete the exact inspected container ID.

The host-capability transaction is stricter because untrusted bytes otherwise execute in the outer/main namespace before authorization and two LiveKit processes cannot own UDP 7882. It is an explicit maintenance-window cutover under both locks: create the replacement stopped with `podman create`; inspect and byte-compare its exact immutable ID/config/image/labels/mounts/security/network request; stage an inactive capability grant and inactive routes for that exact ID/generation; atomically inactivate the old signaling/Twirp routes so no new session can enter it; stop the exact inspected old ID; prove by owner-aware socket inventory that UDP 7882 has no listener; atomically select the new capability grant so the old ID is no longer authorized; only then `podman start <exact-new-id>`; pass semantic health and prove the new PID owns UDP 7882; revalidate the selected grant/ID/generation; and activate the new routes last. Existing clients use the S10 refresh/rejoin path after cutover; this rebuild promises no live-session drain or zero-downtime host-mode replacement. After activation, revoke the unselected old grant and delete the exact old ID. Initial start follows the same sequence with no old-ID steps. `podman run -d`, `podman run`, `--replace`, name-based start/removal, overlapping host-mode processes/grants, or start before exact-ID capability selection is forbidden. A failure before old-route inactivation removes only the inert replacement and leaves the old instance unchanged. A failure at or after old-route inactivation proves routes inactive, stops/removes only the exact replacement if it started, clears the failed selector/grant, and retains the old exact ID stopped; it never automatically restarts/reactivates the old generation. Recovery is a new explicit transaction.

Required adversarial proof: the harness enumerates every eligible managed bridge and active managed instance and proves each succeeds with a valid request-bound JWT; the fixture contains at least two distinct isolated bridges. The expected inspected attachment set must equal the firewall tuple set one-to-one. A foreign network, a foreign container manually attached to a managed bridge, a missing/extra tuple, cross-isolated direct IP, main-namespace direct transport-IP, outer sibling, physical host, wrong interface/IP/destination, stale generation, stale PID, altered nft rule, and unsigned/replayed/misbound JWT all fail. Same-network DNS and ordinary egress continue to work. Host mode reaches only main loopback and still cannot act without the exact generation-scoped capability and JWT.

### DR-TRANSPORT — Atomic Transport Activation

**Decision:** Treat `box-transport.json` and `containers.conf` as one selected generation rather than two independently renamed files.

1. Clear only ephemeral activation state, then complete every Podman/Netavark/pasta/UID/GID/device/helper/retained-container/transport preflight.
2. Create `/run/ploinky/transport/generations/<generationSha256>/` and write canonical compact JSON plus newline and the exact `containers.conf`; set both files `0600`, correct ownership, fsync both files, and fsync the generation directory.
3. Stable file symlinks are `/run/ploinky/box-transport.json -> /run/ploinky/transport/current/box-transport.json` and `/home/podman/.config/containers/containers.conf -> /run/ploinky/transport/current/containers.conf`.
4. Atomically rename one `current` symlink to select the fully written generation, then fsync its parent directory. With no selector, neither stable path resolves. Any failure removes the selector; an unselected ephemeral generation is inert.
5. The record schema is exactly:

```json
{"schemaVersion":1,"address":"IPv4","interface":"ifname","generationSha256":"64hex","containersConfSha256":"64hex"}
```

The generation hash covers canonical record fields and the exact containers.conf bytes without a self-reference. A native test must prove Podman reads `containers.conf` before entering the rootless namespace where `/run` is masked. If that proof fails on either architecture, stop and redesign activation; do not weaken the atomicity guarantee.

### DR-MK — Remove the Built-In Master-Key Fallback

**Decision:** Remove the historical built-in fallback seed (`ploinky-default-master-key-v1`) and do not generate a persistent replacement key in this rebuild.

- Preserve current default resolution exactly: process `PLOINKY_MASTER_KEY`, then the walked-up workspace `.env`, then fail closed. Factor that lookup into `resolveMasterKeySeed({ startDir, env, purpose })`, which returns the exact trimmed raw seed; keep `resolveMasterKey()` as SHA-256 over that seed so every existing derivation byte remains unchanged. The host supervisor passes the canonical host workspace as `startDir`; it never substitutes the Box cwd.
- Use the current `deriveAgentSecret` and `deriveWorkspaceSecret` outputs as the reviewed clean-start contract and freeze them within this implementation. Call both helpers with their existing object API, never a positional string. When a new AES-256 key is needed, the exact conversion is `Buffer.from(deriveWorkspaceSecret({ name: "<domain>", length: 32, encoding: "hex" }), "hex")`; assert the result is exactly 32 bytes before constructing a cipher and zero the owned key buffer after use where the runtime permits. The internal `derived-master` HKDF label remains an implementation detail; the retired `PLOINKY_DERIVED_MASTER_KEY` environment variable is never injected. This does not promise that pre-rebuild encrypted state is readable.
- Freeze and independently vector-test the current store/session/identity domains (`storage/secrets`, `storage/passwords`, `session`, the subject-identity storage domain, generated workspace credentials, and generated per-agent credentials), and add the new clean-start-only `storage/external-turn` and `storage/cloudflare` domains for the two dedicated handle stores. New generated credentials must use an explicit reviewed `deriveWorkspaceSecret` or `deriveAgentSecret` purpose; fixed-vector tests cover the exact object arguments, returned encoding, decoded key length, domain separation, and failure of a positional-string call. No store, session, credential, or identity may consume master bytes directly.
- Keep the `webmeetAgent` manifest declaration of `PLOINKY_WEBMEET_MASTER_KEY` as `generatedSecret: true` in every profile because the rebuilt product still needs a durable room-record wrapping key. That value is for new-build AES-256-GCM room DEK wrapping only and must never serve as the external TURN shared secret or a TURN derivation input. No pre-rebuild encrypted-room fixture, fallback key, dual decryptor, rewrap, or migration is required.
- The outer supervisor calls `resolveMasterKeySeed` and supplies that exact raw seed—not the 32-byte/hash output of `resolveMasterKey()` and not any derived key—only as `PLOINKY_MASTER_KEY` in the environment object of the spawned Podman client process. Its argv contains only `podman exec --env PLOINKY_MASTER_KEY ...`, so Podman copies the named variable into the one inner exec process. The supervisor does not mutate its own global environment and drops its seed reference after spawn. The value never appears in argv, container config, status, logs, journal, fixtures, or artifacts. Fixed vectors include an `.env`-only host invocation whose inner derivation exactly equals direct clean-default derivation from the raw seed, plus a spy that fails if the supervisor forwards the hashed `resolveMasterKey()` bytes instead.
- Each agent receives only its current per-agent root `PLOINKY_AGENT_SECRET`, never the master and never `PLOINKY_AGENT_PRIVATE_SECRET`.
- Derive direction keys with HKDF-SHA256 labels `ploinky/wire/agent-assertion/v1`, `ploinky/wire/router-request/v1`, `ploinky/wire/private-agent-assertion/v1`, and, when the Umami lane is enabled, `ploinky/wire/rate-source/v1`. Root agent secrets are not direct wire-signing keys.
- Once the clean-start derivation/schema vectors for this rebuild are approved, any accidental within-build drift fails tests. Deliberate legacy compatibility or migration work is prohibited unless the root planner receives new explicit scope.

### DR-HARD-CUT — No Backward Compatibility or Migrations

**Decision:** This is a clean-start rebuild, not an upgrade. The accepted current-default user-visible behaviors remain requirements, but no prior Box/runtime/artifact/config/session/store/product schema, encrypted payload, generated credential, image tag, or deprecated manifest field is an input contract.

- Do not implement version sniffing, old-format readers, dual reads/writes, key fallback, re-encryption, data transforms, import-on-start, compatibility aliases, deprecated environment handling, rolling mixed-version support, or downgrade support. Source-absence tests reject these mechanisms.
- Every new persistent record has one exact schema/version and fails deterministically on missing, older, newer, corrupt, or ambiguous bytes. Failure is read-only: do not mutate or delete the incompatible state. Start the rebuild in a fresh workspace/volume set; archiving or deleting an old workspace is an explicit operator action outside this implementation plan.
- This waiver removes compatibility requirements; it does not authorize a repository-wide purge of unrelated current product code or operator data. Hard-cut source-absence enforcement is bounded to the Box/runtime/product contracts explicitly rebuilt in Section 5. An unrelated current-default schema remains untouched unless a named red test and root-planner scope add its exact owner files.
- Runtime/image rollback remains available only before new-format persistent data is written or against a separately preserved clean workspace snapshot. Moving a tag or reverting source is not a data downgrade strategy.
- Incidental readability of old bytes is neither tested nor promised. Conversely, do not gratuitously change clean-default product semantics or cryptographic choices when the rebuild does not require it.

### DR-RELEASE — Land, Publish, and Repin as Separate Transactions

**Decision:** Source preparation, default-branch landing/rebaseline, image publication, consumer repinning, Box assembly, and mutable-tag movement are separate reviewed operations. Implementation work authorizes only branch-local source changes and local builds; it never authorizes a remote default mutation.

| Phase | Allowed mutation | Gate before next phase |
|---|---|---|
| Source-prep commit | Product code/tests/locks; preserve the exact current tested image reference bytes—even when they are a temporary mutable tag or variable—under the S0 allowlist | Unit, source-lock, source-absence, exact-reference characterization, and current regression suites |
| Source landing and rebaseline | A named repository maintainer authenticates one exact accepted-head request to the conforming landing broker under a per-repository authorization; the client has no default-write credential; no image, registry, deployment, or other external-system mutation | Broker final receipt, fresh fetch, landing-parent/tree/provenance equality, new detached clean worktree at the fetched landing SHA, and full regression |
| Image-definition commit | Dockerfile, byte-contract tests, native workflow; no registry mutation | Exact inputs/base digests, local native build, metadata and runtime tests |
| Image-definition landing and rebaseline | The same broker protocol lands reviewed image-definition or dependency-lock commits before a current-tip-gated build | Fresh default equality, clean worktree recreation, image-definition regression, and final KMS-signed receipt |
| Candidate publication | Push architecture-specific candidate by immutable digest in an authorized job | Native amd64 and arm64 gates, SBOM/provenance, signature/digest verification |
| Consumer repin | One reviewed manifest/digest commit per consumer | Registry digest and byte contract verified; no tag or placeholder fallback |
| Consumer-repin landing and rebaseline | A named owner authenticates each reviewed repin as an independent broker transaction; no Box build observes an unlanded/unreceipted repin | Fresh default equality, clean worktree recreation, full consumer regression, and final KMS-signed receipt |
| Box assembly | Exact reviewed source SHAs and fixed consumer digests | All seven SHA equality/current-tip checks and full graph tests |
| Runtime tag move | Move `docker.io/assistos/ploinky-box:runtime` to the verified manifest list | Both native lanes, independent security review, browser/media/release gates |

Rollback moves the mutable tag to the last verified contract-5 manifest digest; running Boxes remain on their inspected immutable image IDs. Consumer repins are reverted independently. Never mutate a running contract-matching Box merely because the tag moved.

Every default landing consumes the organization-operated `ploinky-default-landing-broker`; clients never receive a default-write credential and never invoke `git push`, a provider merge, or a ref-update API. Implementing, deploying, configuring, or installing that broker/GitHub App is shared-infrastructure work outside this rebuild and requires separate organization-owner authority. G1 is blocked unless every affected GitHub organization supplies a signed current broker-conformance/trust bundle and the production broker passes the exact contract tests below. A local fake broker is test evidence only and never authorizes a real ref update.

The immutable per-repository approval contains an authorization ID; canonical GitHub repository URL and node ID; exact fully qualified candidate and default refs; expected pre-landing default OID; accepted implementation commit and tree; canonical patch SHA-256 against that base; required test-transcript SHA-256 values; fresh reviewer acceptance; method `github-update-refs-broker-v1`; the approved maintainer's organization-SSO subject plus GitHub login and immutable user node ID; approved GitHub App ID/slug and installation ID; one-shot admission expiry; separately named revert owner; and the SHA-256 of the signed broker trust bundle. `DEFAULT_REF_FULL` and `CANDIDATE_REF_FULL` must each match `^refs/heads/[A-Za-z0-9._/-]+$` without `..`, `//`, `@{`, a trailing slash/dot, or a backslash and must pass `git check-ref-format`; they must differ. The accepted commit must already be the exact remote candidate-ref tip so the broker can address an existing object without accepting source bytes from the caller. Pushing or replacing that non-default candidate ref is part of ordinary reviewed branch preparation and grants no default-write authority.

`LANDING_TOOL_ROOT` is the read-only accepted S2 container-image-builds worktree whose tree and exact client/schema/root-public-key hashes are named in the approval; it is not resolved from PATH or an unverified environment override. The organization signer supplies an owner-signed trust bundle binding the HTTPS broker origin, TLS identity, OIDC issuer/audience, GitHub App identity and permitted installations/repositories, receipt-signing KMS key ID/public key, and validity interval. Only the offline trust root public key is checked in. GitHub user tokens, App keys, OIDC credentials, database credentials, and KMS/HSM signing keys remain solely in the broker/identity platform and never enter a repository, client argv/environment, log, or artifact.

One broker transaction performs this exact state machine:

1. Authenticate the requesting maintainer with a short-lived, audience-bound organization identity token supplied to the client only on inherited FD 3. Map its immutable subject to the approval's GitHub user node ID and require a broker-held GitHub App **user access token** for that same user/App/installation; an installation token, personal token, different user, or client-supplied GitHub credential is rejected.
2. In a serializable durable transaction, acquire the single repository/default-ref lease with a monotonically increasing fencing token. An unresolved transaction blocks a new lease. Canonical-verify the approval/trust signatures and hashes, admission expiry, actor/App/installation/repository/ref fields, candidate/default tips, accepted commit/tree/patch/tests/review, clean fast-forward ancestry, current branch/ruleset checks, and absence of historical Box ancestry.

2. Every remote-default mutation uses DR-RELEASE's separately authorized one-shot broker transaction. Only the exact accepted head may land through one GitHub `updateRefs` entry with the signed fully qualified ref, exact `beforeOid`/`afterOid`, and `force=false`, after fenced admission by the authenticated approved maintainer+App identity. Client Git/provider writes, ordinary push, provider merge, squash/rebase, force/lease, reset, and protection bypass are rejected.
3. After every broker update attestation, re-fetch into a newly allocated detached clean worktree, prove accepted-head ancestry and exact accepted-tree equality, rerun the full repository regression, and submit signed CI evidence while the transaction stays fenced. A current-tip build may consume only the final KMS-signed receipt's fetched SHA; an update attestation or unresolved/unreceipted transaction is insufficient.
4. Source-producing workflows validate their selected current default branch and exact current tip; `refs/heads/ploinky-box`, an implementation branch, or an unlanded commit is rejected.
5. Box assembly accepts explicit reviewed full SHAs and additionally proves each equals its landing receipt, source lock, checkout, and freshly fetched selected default tip at dispatch. Checkout `HEAD` must equal the input, and the worktree must be clean.
6. Candidate artifacts are addressed by digest. Tests never execute a mutable tag when a candidate digest is available.
7. Candidate publication and consumer repin occur in different reviewed commits/jobs. A consumer never lands a digest that has not passed both native lanes. The Wave A definition landing → candidate/index publication → Wave B dependency-lock landing → dependent candidate/index publication → S15 repin commit/landing → S16 Box-definition landing DAG is mandatory; jobs cannot flatten it into one authorization or workflow mutation.
8. A failed landing or post-landing regression is recovered only by a separately reviewed and authorized revert commit through the same protocol, followed by another clean rebaseline. No image build proceeds from the failed SHA, and no source revert claims persisted-data downgrade support.
9. Mutable `ploinky-box:runtime` moves only in S17 after the complete immutable manifest and every release gate. Existing Boxes continue using their immutable inspected IDs.

## 11. Stop Conditions and Final Plan Acceptance

Stop implementation and return to the root planner if any of these occurs:

- Native Linux amd64 cannot reproduce the accepted Q8 reachability/denial model, or either architecture cannot atomically consume the transport selector through the masked `/run` namespace.
- Rootless nftables cannot install/read back the exact table atomically, readback normalization is ambiguous, or another owner already uses the proposed table/chain boundary.
- A forwarder cannot be supervised without an unverifiable PID/listener takeover window, or a Router restart would require topology/firewall repair rather than read-only verification.
- A component would require a legacy reader/writer, fallback key, dual schema, migration, import-on-start, automatic data deletion, mixed-version operation, or downgrade path instead of the DR-HARD-CUT clean-start contract.
- Any product requires a third physical port, wildcard 8081, a public product listener, gateway/sidecar resurrection, source inside the runtime image, or a mutable consumer reference to one of the ten shared images rebuilt in S14.
- Exact upstream source objects, full lock hashes, native image digests, provenance, selected public IPv4, external TURN ownership, or existing Cloudflare tunnel/zone/scope cannot be verified.
- A repository default cannot be landed by its named authorized maintainer through the conforming actor/App-bound, one-shot, fenced broker `beforeOid`/`afterOid`/`force=false` transaction, or the fetched landing SHA cannot equal the accepted head/tree/ancestry, or the new clean worktree, complete regression, final KMS-signed receipt, and revert owner cannot all be proven before a current-tip-gated build.
- The signed release approval, canonical Box-host identity, literal assigned target IPv4, locked scanner/collector bytes, before/after complete cross-UID socket owners, XML target, or evidence signatures/nonces cannot be made identical and complete.
- A required edit falls outside Section 5, a current-default regression lacks an intentional disposition, or historical code would overwrite a current DS/current behavior.
- Old private tuple removal cannot be proven. Close the lane and retain the old container; never continue by deletion.
- Registry authority has not been granted for the S14 publication substep or S17 Box publication/tag move, or Cloudflare, TURN, production, deployment, scanner, or browser-account authority has not been granted for the corresponding S17 action. Stop at the preceding local gate; do not infer authority.
